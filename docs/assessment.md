# liteOS 安全、可靠性与性能评估

> 评估对象：当前 x86_64 与 riscv64 原型  
> 评估环境：QEMU，100 Hz 执行节拍  
> 评估结论：**语义与边界行为已通过当前测试，性能余量充足；但尚不具备生产级安全隔离。**

## 1. 结论摘要

liteOS 当前原型已经证明其核心模型可运行：基座只管理接线有效性并转发唯一的运动原语，物件自行保存状态、解析参照系并按外部执行层推进。x86_64 与 riscv64 使用相同的 `base/` 实现，并通过相同的语义测试与压力测试。

当前可以成立的结论：

- 两个架构的语义自检均为 `failures = 0`。
- 性能与压力测试均为 `bench failures = 0`。
- 20,000 次反复插拔后，世代号持续推进，最早句柄保持失效。
- 表满时返回 `WIRE_NONE`，已有接线不受破坏。
- 死句柄和 6 类伪造句柄均被拒绝。
- 在填满所有可用物件槽、参照链最深为 8 层的测量中，一次完整推进只占 100 Hz 节拍周期约 1% 至 2%。
- 当前没有用户态、W^X、NX 强制隔离或上层大脑沙箱，因此不能称为生产级安全系统。

## 2. 验证范围与方法

### 2.1 语义验证

`base/verify.c` 验证以下内容：

- 唯一运动原语及错误返回值。
- 大脑与普通物件使用同一种接线模型。
- 物件自述能力与自持状态。
- 参照系链解析、断链和成环拒绝。
- 参照系四元数对线运动与角运动的旋转。
- 不同 `period_ns` 的执行节奏。
- 迟到运行只推进一次，不补跑。
- 符合性要求 R1–R3；R4 与 R6 由类型边界保证。

### 2.2 压力验证

`base/bench.c` 验证：

- 接线表和物件表达到容量上限后的故障关闭行为。
- 表满后已有接线仍可接受运动事件。
- 槽位复用产生新世代句柄。
- 离开后的旧句柄保持失效。
- 6 类伪造句柄不会成为有效接线。
- 20,000 次插入和拔出循环中的世代推进。

### 2.3 性能测量

测量全部在目标内核中执行：

- x86_64 使用 TSC。
- riscv64 使用 10 MHz `time` CSR，一格为 100 ns。
- 绝对计数值受 QEMU 和宿主机影响，不能当作真实芯片的纳秒性能承诺。
- `worst run share of a tick` 使用同一个计数器测量分子和分母，是本报告最可靠的性能指标。

复现命令：

```sh
make ARCH=x86_64
make ARCH=riscv64
tools/bench.sh
```

## 3. 最终测量结果

以下结果来自一次完整的双架构运行。虚拟机绝对计数会波动，比例更有解释价值。

| 指标 | x86_64 | riscv64 |
|---|---:|---:|
| 进入基准时空余物件槽 | 58 | 62 |
| `base_apply` 合法路径 | 482.48 TSC 计数/次 | 1.80 time 计数/次 |
| `base_apply` 拒绝路径 | 101.17 TSC 计数/次 | 0.96 time 计数/次 |
| 1 层参照链解析 | 437.89 TSC 计数/次 | 1.19 time 计数/次 |
| 8 层参照链解析 | 6666.44 TSC 计数/次 | 29.24 time 计数/次 |
| 最坏完整推进 | 351222 TSC 计数 | 1410 time 计数 |
| 一个 100 Hz 节拍周期 | 28108316 TSC 计数 | 89634 time 计数 |
| 最坏推进占节拍 | **1.24%** | **1.57%** |
| 热插拔循环 | 20,000 | 20,000 |
| 基准失败数 | 0 | 0 |

x86_64 的空余槽位为 58，是因为 PCI 扫描保持 6 个设备在线；riscv64 的空余槽位为 62，是因为测试配置保持 2 个 PCI 设备在线。这不是泄漏。自检曾遗留 `brain2`、`hand`、`foot` 三个物件，现已在测试结束时归还。

### 性能解读

- 合法 `base_apply` 比拒绝路径更贵，因为合法路径需要查找目标物件并提交事件；拒绝路径在句柄校验处提前返回。
- 8 层参照链明显比 1 层链贵，符合逐层旋转和叠加的线性工作量预期。
- 即使把所有可用槽位填满，并令物件处于最深参照链，一次完整推进仍只占一个 10 ms 节拍的约 1% 至 2%。
- 当前原型具有充足的 100 Hz 负载余量，但没有证明在真实芯片、高频控制、更多物件、SMP 或生产工作负载下仍保持同样结果。

## 4. 安全评估

### 4.1 已验证的安全属性

| 属性 | 结果 | 证据 |
|---|---|---|
| 表满故障关闭 | 通过 | 额外插入返回 `WIRE_NONE` |
| 已有接线不受表满破坏 | 通过 | 满表后全部已有接线仍可接受事件 |
| 死句柄不复活 | 通过 | 槽位复用后句柄改变，旧句柄失效 |
| 伪造句柄拒绝 | 通过 | 6 类边界和错误形状均被拒绝 |
| 参照链成环检测 | 物件侧通过 | 基座看不到链，`object_resolve` 拒绝循环 |
| 断开的参照系拒绝 | 通过 | 参照物件离开后解析失败 |
| 容量测试不污染后续状态 | 通过 | 基准结束后归还所有临时物件 |

### 4.2 已确认的安全缺口

#### x86_64（当前已装上）
- EFER.NXE 置位，2 MiB 以上共 511 个大页项带 NX；内核第 0 页（代码、.rodata、.data/栈同页）保持 RWX，因为 2 MiB 是当前唯一页粒度。
- CR0.WP 置位：内核态写也必须遵守页表项的可写位。当前没有哪一页标只读，所以 WP 只是接通语义，不会立刻拦截任何写。
- 这不是完整 W^X：代码与数据仍同在第 0 页。要真正做到代码 RX、数据 RW+NX，需要 4 KiB 页表重建，不在本阶段。

#### riscv64（当前已装上）
```text
satp = 0x8000000000080217  (MODE=8 Sv39)
```
- Sv39 4 KiB 页已启用：.text R|X、.rodata R、.data/.bss/栈 R|W；UART（0x10000000）和 PCIe ECAM（0x30000000）各映射一个 2 MiB 大页 R|W。
- 仍没有 U 态：S 态可改 satp，所以这里拦的是「写错/跳错地址」，拦不住恶意内核修改页表。
- PMP 与分页是两道检查：PMP 放行 ≠ 分页放行，切换 satp 后设备仍必须在页表内。

#### 架构层面共同缺口

- 没有用户态进程或特权隔离。
- x86_64 未做到完整 W^X（2 MiB 粒度限制）；riscv64 已做到 W^X 但无 U 态。
- 没有上层大脑沙箱；错误或恶意大脑可以破坏基座和其他物件。
- 基座模型刻意不授权：任何持有有效句柄的调用者原则上可以命令任意活接线。
- 物件申报的限位和最大速率不会由基座强制执行。
- `base/` 与 `object.c` 没有锁，不保证 SMP、抢占或中断上下文重入安全。
- 构建使用 `-fno-stack-protector`，且没有栈守卫页。
- 每槽世代号为 32 位，世代耗尽后槽位永久退休，不再复活旧句柄；世代耗尽是部署层面的拒绝，不是永不拒绝。
- 已有确定性模糊语料 `tests/host/fuzz_base.c` 与生成耗尽白盒测试 `tests/host/test_wire.c`，但尚无形式化证明或硬件故障注入覆盖。

因此，当前安全结论必须表述为：

> liteOS 已证明其句柄边界和容量边界具有良好的拒绝行为，并已在两架构上打开页级权限（x86_64 NX+WP 在当前粒度下尽力而为；riscv64 Sv39 达到 W^X）。但仍无用户态与大脑沙箱，没有授权模型；生产级内存安全尚未实现。

## 5. 可靠性评估

### 已证明

- 两架构运行同一套基座语义。
- 自检、压力测试均为零失败，门禁覆盖 `failures / bench failures / brain failures / monitor failures / mmu failures`。
- 迟到运行不会在一次调用中补跑多步。
- 物件位置与实际执行步数一致，例如速度为 3 时，99 步得到位置 297。
- riscv64 通过 SBI TIME 扩展编程定时器，避免 S 态直接访问被 PMP 禁止的 CLINT；定时器中断只累加节拍，物件执行留在主循环。
- 自检与基准产生的临时物件均在结束时归还。
- riscv64 Sv39 翻译已启用并通过三表页 walk 自检；x86_64 NXE 与 CR0.WP 已置位并自检。
- 确定性模糊语料（可证伪变异体已实测）与世代耗尽白盒测试都已进入 CI 门禁。

### 需要正确理解的现象

`tick_count` 与物件步数可能相差一小步。原因是决定 16 明确规定：迟到的一次 `object_run(now_ns)` 只推进一次并从当前时刻重新排期，不对错过的节拍补跑。这优先避免延迟后突发执行大量陈旧动作。系统会同时打印节拍数和步数，使该现象可观测。

### 尚未证明

- 长时间连续运行后的资源稳定性。
- 电源故障、设备抖动、总线错误和中断风暴恢复。
- SMP、多 hart、多核并发安全性。
- 驱动错误隔离和上层大脑崩溃后的恢复。
- 多级 PCI 桥与运行时 riscv64 PCIe 热插拔。
- 真实硬件上的缓存、内存序和定时行为。

## 6. 是否“极速”

自动门禁采用 QEMU `-icount shift=0,align=off,sleep=off`，使用固定指令推进形成可重复的回归基线。普通 QEMU 运行曾出现 p99.9 超过一个节拍、最大值超过三个节拍的宿主调度离群值，因此不适合作为函数级预算门禁。以下数据只表示 icount 回归基线，不是物理芯片纳秒或 WCET 证明。

| 满表 `object_run` 指标 | x86_64（58 物件） | riscv64（62 物件） |
|---|---:|---:|
| 平均值 | 732,413 ticks，节拍占比 9.07% | 6,785 ticks，节拍占比 7.74% |
| p50 | 743,669 ticks | 6,888 ticks |
| p99 | 745,286 ticks | 6,901 ticks |
| p99.9 | 745,286 ticks，节拍占比 **9.23%** | 6,901 ticks，节拍占比 **7.87%** |
| 最大值 | 745,286 ticks，节拍占比 **9.23%** | 6,901 ticks，节拍占比 **7.87%** |
| 直方图 | 99 样本落在 2^18 桶，1,901 样本落在 2^19 桶 | 2,000 样本全部落在 2^12 桶 |

自动预算是：p99.9 小于一个 100 Hz 节拍的 50%，最大值小于 75%。两个架构当前均通过。测量时短暂关闭目标中断，只衡量 `object_run` 自身；中断暴露的端到端尾延迟必须在后续风暴场景中单独测量。

在当前定义的 100 Hz、最多 64 个物件、最多 8 层参照链的原型负载下，可以说：

> liteOS 在确定性 QEMU 回归基线上满足当前函数级尾延迟预算；真实硬件和端到端实时性仍未验收。

不能说：

> liteOS 已经在所有硬件和生产负载下证明为极速。

原因是当前运行在 QEMU，工作负载规模固定，没有真实设备控制闭环、SMP、缓存压力、网络中断风暴或真实芯片测量。

## 7. 生产级安全前的必做项

建议按以下顺序推进：

2. **建立授权模型，但不污染运动本体论**
   - 授权应位于接线管理或上层策略层，不把权限字段塞进 `motion_event_t`。
   - 使用不可伪造能力句柄或每连接域的允许目标集合。

3. **强化运动边界**
   - 由物件或安全监护大脑依据 `object_capability_t` 强制限位、最大速率和最大加速度。
   - 基座仍只处理运动，不保存世界状态。

4. **并发与故障恢复**
   - 明确单核假设，或为接线表和物件表建立锁与内存序规则。
   - 增加大脑崩溃、设备离开、中断风暴和重复热插拔测试。

5. **验证门禁**
   - 在 CI 中对 x86_64 和 riscv64 执行构建、自检和 `tools/bench.sh`。
   - 加入 clang 静态分析、UBSan 可宿主化单元测试、模糊测试和长时间 soak test。

## 8. 最终判定

| 维度 | 判定 |
|---|---|
| 核心思想可行性 | **通过当前原型验证** |
| 双架构一致性 | **通过** |
| 句柄与容量边界可靠性 | **通过当前压力测试** |
| 100 Hz 原型性能 | **性能余量充足** |
| 生产级内存安全 | **不通过，尚未实现隔离** |
| 恶意或错误大脑隔离 | **不通过，尚无沙箱和授权** |
| SMP 与长期运行可靠性 | **尚未验证** |

最终准确结论：

> liteOS 已经从概念进入可运行、可测量、可复核的双架构原型阶段。它的运动控制模型、句柄边界和当前规模下的性能已经得到支持性证据；安全隔离仍是下一阶段必须完成的工程，而不是已经具备的属性。
